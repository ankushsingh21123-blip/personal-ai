## 1. Trending open-source personal-AI / agent repos and frameworks

### 1.1 Personal agents: the gateway pattern won, and its risks are now documented

**OpenClaw (ex-Clawdbot / Moltbot) — MIT, TypeScript.** First published 24 Nov 2025 as Warelay, renamed Clawdbot (2 Jan 2026), Moltbot (27 Jan 2026, after an Anthropic trademark objection), then OpenClaw (30 Jan 2026). Self-hosted personal agent that lives in messaging apps (WhatsApp, Telegram, Signal, Discord, Slack), connects a frontier model to real tools, and runs 24/7 on the user's own machine. Reported at ~392,885 stars on 24 Oct 2026 and ~394,000 on 1 Nov 2026, making it one of the most-starred repos in GitHub history. Creator Peter Steinberger joined OpenAI in Feb 2026; the project moved to an independent non-profit foundation and stayed MIT. OpenClaw 2.0 shipped 30 Aug 2026 with easier install and a new interface. [secondary — coverage round-ups, Oct–Nov 2026]

- Sources: https://www.ayautomate.com/blog/openclaw-open-source-ai-agent (updated ~7 Nov 2026); https://techlara.se/ainews/what-is-openclaw (21 Oct 2026); https://xcloud.host/what-is-openclaw/ (updated ~12 Nov 2026).
- **Winning pattern for Piplet:** the agent lives where the user already talks; the model is interchangeable; everything runs on the user's hardware. Piplet already follows this shape (Telegram/WhatsApp scaffolding, multi-provider brain). The differentiator is not the shape — it is the deny-first posture.
- **Risk pattern, equally important:** in Feb 2026 Koi Security reviewed 2,857 skills on ClawHub and found 341 malicious ones (per TechLara, 21 Oct 2026). The prior cycle's file records a one-click RCE (CVE-2026-25253, patched Jan 2026) and 1,000+ malicious skills pulled. Lesson: an open skill/plugin registry without review is an attack surface. Piplet's allowlist + human-reviewed skills (§5, item 3) is the right counter-pattern; never auto-install third-party skills.

**The 2026 "bot wars" — every lab shipped a personal agent.** A 30 Oct 2026 round-up records: Nous Research's Hermes Agent (Feb 2026, MIT, persistent memory); xAI's Grok Bot (beta 11 Aug 2026, per-agent cloud computer); Meta's Muse (8 Sep 2026); OpenAI's dots (DevDay, late Sep 2026); Anthropic's Claude Duet (late Oct 2026, waitlisted research preview); Microsoft's Scout (built on the OpenClaw framework). [secondary]

- Source: https://www.thenewfabric.com/blog/the-great-bot-wars-of-2026 (30 Oct 2026).
- **Implication:** a generic personal assistant is now a crowded, lab-funded category. Piplet's defensible ground is narrower: a $0, self-hosted, deny-first agent that a solo founder actually dogfoods, plus one narrow B2B workflow done reliably (§3, §5 item 11). Do not try to out-feature the labs.

**Hermes Agent (Nous Research) — MIT.** Launched 25 Feb 2026; the learning loop (a "Curator" that reflects on runs and writes reusable Markdown skills) remains the one idea worth copying as a *pattern*, with human review before any learned skill is trusted. See the prior cycle's file §2.1 for the full verdict; this cycle adds the caution from §1.5 below (self-written skills can drift; Anthropic's Oct 2026 guidance prefers curated, human-written skills).

**DeepSeek Harness (dsh) — MIT, developer preview.** Launched Aug 2026; everything-is-a-plugin architecture; points at any OpenAI-compatible endpoint including Ollama. Still pre-1.0 with breaking changes promised and no security audit (per the prior cycle's file). **Watch only.**

**Agent Zero — MIT.** Docker desktop + sub-agents + MCP/A2A; the v2 sandbox candidate. Heavy and Docker-required; keep as the sandbox reference, not the base (prior cycle's file §2.1).

**Convergent lessons (all three round-ups agree):**

1. **Durable execution + human approval are the production features.** Checkpointing, resume-after-crash, and mid-run interrupts matter more than multi-agent cleverness. Piplet's SQLite-backed queue/routines/freeze already rhyme with this; the gap is a durable, resumable *agent run* with approval interrupts (§5, items 2 and 7).
2. **Every framework now consumes MCP servers**, so tool integrations survive a framework switch. Build tools behind a protocol boundary, not inside one framework (§5, item 5).
3. **Framework licences are free (MIT/Apache-2.0); the bill is tokens + hosting + tracing.** The $0 constraint is about model routing and self-hosting, not framework choice.
4. **For a single agent with a small tool list, a plain loop + function calling is still sufficient** (prior cycle's file §2.1, citing the literature). Do not adopt a framework until Piplet's jobs outgrow the loop. The trigger to revisit: long multi-step jobs that must survive restarts and pause for approval mid-run.

**n8n** (~206k stars, Oct 2026; fair-code/Sustainable Use licence — source-available, *not* OSI open source): best visual workflow automation; fine to *use*, careful about *selling* as part of a product. Keep for workflows (already used for the Nova machine). [secondary — prior cycle's file §2.9]

### 1.3 The protocol layer: MCP, A2A, and Agent Skills (2024–2026)

**Model Context Protocol (MCP).** Published by Anthropic in Nov 2024 as an open JSON-RPC standard for agent↔tool discovery and calling. In 2025 OpenAI, Microsoft, Cursor, Zed and most frameworks adopted it. On 9 Dec 2025 Anthropic transferred MCP to the newly founded Agentic AI Foundation under the Linux Foundation. The Mar 2025 spec revision (2025-03-26) added Streamable HTTP transport (replacing HTTP+SSE) and an OAuth 2.1 authorisation framework. By mid-2026 there were thousands of community servers (GitHub, Notion, Postgres, AWS, browser automation).

- Sources: https://blckalpaca.at/en/knowledge-base/ai-agents/model-context-protocol-mcp/mcp-security-best-practices (Oct 2026); https://www.openlegion.ai/en/learn/model-context-protocol (2026); https://www.navokit.com/en/blog/model-context-protocol-mcp-architecture (25 Aug 2026).
- **Security pattern (critical for Piplet):** MCP is a *capability-exposure* protocol, not an authorisation or audit protocol. It does not standardise call logging, budgets, or approval. Production deployments must layer on: authentication, per-server sandboxing, least-privilege scopes, strict schema validation (Zod/Pydantic) before shell execution, explicit approval gates for destructive tools, and per-agent tool-call budgets. Documented risks: indirect prompt injection via tool results (reference case EchoLeak, CVE-2025-32711, disclosed by Aim Labs, June 2025; Invariant Labs mechanism write-up 1 Apr 2025, WhatsApp PoC 7 Apr 2025), tool poisoning via manipulated server descriptions, overly broad permissions, insecure token handling. Mitigation summary from the literature: sandboxing + scope-limited tokens + least privilege + human approval, and never let agents autonomously install MCP servers from untrusted registries.
- **MCP Apps (SEP-1865, stable 26 Jan 2026):** the first official MCP extension — a tool can return an interactive UI (form/chart/dashboard) rendered in a sandboxed iframe, communicating via `postMessage`. Mandatory sandboxing + CSP from declared domains. A Jan 2026 Goose issue showed a UI rendered *before* user approval in manual-approval mode (fixed 21 Jan 2026) — a reminder that approval must gate rendering too, not just execution. [secondary]
  - Source: https://eslamhamed.com/blog/mcp-apps-first-official-mcp-extension-interactive-ui (6 Nov 2026).

**Agent2Agent (A2A) protocol.** Launched by Google with 50+ partners; standardises agent-to-agent discovery and communication. Now, with MCP, under the Agentic AI Foundation. CrewAI and OpenAgents support it; LangGraph/AutoGen needed custom integration as of early 2026. **Watch** — relevant only if Piplet ever needs to hand work to another agent system.

**Agent Skills (open standard, Dec 2025).** Anthropic published Agent Skills as an open specification on 18 Dec 2025 and handed governance to the Agentic AI Foundation; Microsoft, OpenAI and Google shipped support within days; by June 2026 ~40 compatible products were listed (VS Code, Codex, Cursor, Gemini CLI, GitHub Copilot, Databricks). A skill is a folder with a `SKILL.md` (name + description frontmatter + Markdown instructions, optionally scripts). The rule of thumb from Anthropic's docs: "If you're explaining how to do something, that's a skill. If you need Claude to access something, that's MCP." A third rule from practitioners: if the work would flood the conversation with output nobody re-reads, that's a subagent.

- Sources: https://tao-hpu.medium.com/skill-is-knowledge-agent-is-execution-context-bc8cce4f9cf1 (8 July 2026); https://promptsrush.com/blog/claude-skills-vs-mcp-vs-subagents (checked 25 Oct 2026, MCP spec rev. 2026-07-28).
- **Anthropic's Oct 2026 guidance — fold subagents into skills:** On 22 Oct 2026 Anthropic published "Building agents: When to fold subagents into your main agent loop" (Diane Sarkis). Finding from its Applied AI team: across several enterprise deployments, a single agent with skills frequently outperformed both one-prompt-for-everything and subagent designs on quality, often at lower cost and latency. The mechanism is *progressive disclosure*: the agent sees short skill/tool descriptions, and full content loads only when needed (this cut Claude Code's own system prompt by over 80% for advanced models). Subagents still fit genuinely parallel work and context-bloat isolation. Anthropic's closing advice: build a small end-to-end eval, fold in one subagent, keep it as a subagent only if the folded version scores worse. Multi-agent systems use ~15× the tokens of chat interactions vs ~4× for single agents (Anthropic research-system write-up, June 2025, cited therein). [secondary]
  - Source: https://enjoy.dev/blog/skills-vs-subagents/ (Oct 2026).
- **SkillsBench (Feb 2026, 87 tasks, 8 domains, 77 authors):** curated, human-written skills raised task pass rates by 16.2 percentage points on average across seven model-harness configurations; self-generated skills scored slightly negative. Snyk's ToxicSkills audit scanned 3,984 public skills and found prompt-injection techniques in over a third (~1,500 malicious payloads). [secondary, via the Medium piece above — VERIFY BEFORE CITING publicly]
- **Piplet implication:** skills (curated, human-reviewed, progressively disclosed) are the cheapest capability multiplier available, and they fit Piplet's existing `skills/` folder. They are ranked #3 in the backlog.

### 1.4 Memory layers: retrieval is table stakes; time-awareness and locality are the frontier

**Mem0 — Apache-2.0, Python + TypeScript SDK.** "The Memory Layer for AI Agents." An app sends conversation messages; an LLM distils them into short fact-like memories stored with embeddings and searched later, scoped by user/session/agent. Hybrid storage (vectors + graph + key-value); open-source library runs locally (default: local Qdrant); hosted Platform adds graph memory and compliance docs. Reported ~68,112 stars / 8,073 forks on 30 Oct 2026; paper arXiv 2504.19413 (28 Apr 2025). YC S24; reported $24M Series A, Oct 2025. Pricing reported in 2026 guides: Free (10k memories), Developer $19/mo, Pro $249/mo (graph memory, SOC 2 Type II/HIPAA docs). Caveats carried forward from the prior cycle: graph memory was removed from open source in Apr 2026 (Platform-only); extraction is add-only (stale facts persist without a pruning job); telemetry on by default; headline benchmarks are managed-platform numbers. A Zep rebuttal (6 May 2025, modified June 2026) and a Letta comparison (12 Aug 2025) dispute Mem0's benchmark methodology — do not quote any single vendor's memory numbers without noting the dispute. [secondary]

- Sources: https://lucagattoni.github.io/knowledge-graph-tutorial/kb-kg/projects/mem0/ (repo metadata read 30 Oct 2026); https://baeseokjae.github.io/posts/mem0-agent-memory-guide-2026/ (2026); https://www.oreilly.com/radar/the-open-source-agent-toolkit-in-2026/ (2026).

**Letta (formerly MemGPT) — fully open source, self-hostable, model-agnostic.** Treats memory like an OS: main context is RAM, archival memory is disk, and the agent itself decides what to promote, archive, or forget. Right model for agents running autonomously for days; harder to deploy and debug than a hosted endpoint because memory decisions happen inside the agent at runtime. Independent evals cited in one 2026 comparison put it around ~83% on LoCoMo, the highest verified score among the classic open-source tools. [secondary]

**Zep / Graphiti — temporal knowledge graph.** Every fact is timestamped, so contradictions over time ("user said X last week, says Y today") can be resolved; handles entity resolution ("Alice" = "alice@acme.com" = "the CEO"). Cost warning from O'Reilly's 2026 toolkit survey: Zep's memory footprint per conversation runs past 600,000 tokens vs Mem0's 1,764 in one comparison, and the LoCoMo-winning configuration ran ~340× heavier per conversation than the runner-up — a difference no benchmark column shows. Graphiti is open; the full Zep platform is SaaS from ~$25/mo. [secondary]

**MemPalace — MIT, local-first, verbatim storage (UNVERIFIED HYPE — treat with caution).** One 2026 comparison claims ~54.1k stars, v3.4.0 on 6 June 2026, 96.6% R@5 on LongMemEval with zero API calls and 88.9% R@10 on LoCoMo, native MCP, fully local. These claims were **not** corroborated by any other source in this sweep and the comparison reads as promotional. **Do not adopt or cite until the repo, licence file, and benchmark harness have been read directly.** The *pattern* (local-first verbatim recall, no embedding bill) is still worth noting. [secondary, single-source — UNVERIFIED]

- Source: https://rohitraj.tech/notes/open-source-ai-agent-memory-mem0-vs-zep-letta-2026 (2026).

**Piplet implication:** the prior cycle's verdict stands — sqlite-vec inside the existing SQLite file first (zero new infra), mem0 self-hosted later only if extraction quality is needed. What this cycle adds: timestamp every fact, keep contradictions visible instead of silently overwriting, and give the user a visible forget/edit control (§5, item 4). Memory cost per conversation is a metric to track, not just recall accuracy.

### 1.5 Browser and computer use: DOM-first is shippable; screenshot-clicking is expensive and still flaky

Reads and labels DOM elements; model-agnostic (OpenAI/Anthropic/Google, its own model, or Ollama). Vendor-reported 89.1% on WebVoyager (586 live-site tasks, GPT-4o). **But:** a human-judged study by Ohio State + UC Berkeley researchers ("An Illusion of Progress?", arXiv Apr 2025, revised Oct 2025) found browser-use completed only 30.0% of Online-Mind2Web tasks under human judging, vs the vendor's 89.1% on the older WebVoyager with the same model; browser-use's own March 2026 run on the same benchmark with its own agentic judge reported 97%, and its Aug 2026 post showed the same runs scoring 62.5–83.7% depending on the judge. Judge choice moves the number more than the agent does. [secondary]

- Sources: https://gengrades.com/browser-use (Oct 2026); https://particula.tech/blog/browser-use-vs-operator-vs-claude-computer-use-web-agents (2026).

### 1.6 Sandboxing: microVMs are the 2026 default for untrusted code; secrets stay outside

The industry converged in 2025–2026 on microVMs (Firecracker, ~150ms cold start, hardware VM boundary) as the baseline for production multi-tenant agent execution, with gVisor as the syscall-interception alternative. OS-level isolation (bubblewrap on Linux, Seatbelt on macOS — used by Claude Code and Codex CLI) is a step below. Containers alone are *not* the boundary for untrusted code: several 2025 container-escape CVEs are cited (e.g. CVE-2025-31133 runc `maskedPaths` bypass; CVE-2025-23266 NVIDIAScape). A 2026 BeyondScale report cited in one survey found 88% of organisations reporting confirmed or suspected AI-agent security incidents in the past year. Trail of Bits (Oct 2025) showed pre-approved commands in three major agent platforms create argument-injection surfaces (e.g. `go test -exec`, `git show --format` achieving RCE without triggering approval flows) — approval must cover the *full* command including flags, not just the base command. [secondary]

- Sources: https://www.architectviewmaster.com/blog/sandboxed-agents-giving-your-code-monkeys-their-own-sandbox/ (2026); https://www.everstack.ai/blog/sandboxing-ai-generated-code/ (2026); https://www.taskade.com/blog/ai-agent-sandboxes (Oct–Nov 2026, 20 options compared).

**Platforms (licences as reported — re-check before adopting):**

- **E2B** — Apache-2.0 (two repos), Firecracker microVMs, ~150ms cold start (<30ms from snapshots), self-hosting documented (Terraform, GCP GA, AWS beta), usage grew from 40k sandbox sessions/mo (early 2024) to ~15M/mo (Mar 2025). Pricing from free, ~$0.05/hr for 1 vCPU (as reported). No GPU sandboxes as of late 2026 (per one survey). Concurrency tiered (20 Hobby / 100 Pro).
- **Vercel Sandbox** — GA 30 Jan 2026, Firecracker microVMs, CLI/SDK open-sourced (SDK only).
- **Daytona** — pivoted Feb 2025 to agent code execution (27–90ms provisioning via warm pools, unlimited execution windows). **Licence warning:** one Aug–Oct 2026 analysis reports the open-source repo received no updates since June 2026, core development moved to a private codebase, and the `LICENSE` file was deleted 23 June 2026 (GitHub reports no licence); last open release v0.190.0 was AGPL-3.0; docs say default sandboxes are Linux containers while the README claims a dedicated kernel. **Do not build a security boundary on the Daytona self-hosted snapshot without verifying this directly.** Hosted product unaffected.
- **Anthropic `@anthropic-ai/sandbox-runtime`** — open-source package published Nov 2025 (per one survey; verify).
- **Dagger Container Use** — open source, June 2025: one ephemeral container + dedicated Git worktree per coding agent, enabling parallel conflict-free work.

**Design rules that matter more than the isolation primitive** (Everstack/Taskade, 2026): the agent loop runs *outside* the sandbox; secrets stay *outside* the sandbox (never put provider API keys in the sandbox environment; block the cloud metadata endpoint `169.254.169.254`); network egress goes through an allowlist (a microVM with unrestricted egress is worse than a container with none, because exfiltration needs no escape); filesystem mounts are minimal and read-only by default. Two named threat models: Simon Willison's "lethal trifecta" (June 2025) — an agent is exploitable when one context combines access to private data + exposure to untrusted content + ability to communicate externally; Meta's "Rule of Two" (Oct 2025) — an agent session should satisfy no more than two of: processing untrustworthy input, access to sensitive systems/private data, ability to change state or communicate externally. [secondary]

**Piplet implication:** Piplet's current shell tool runs on the host with an allowlist. That is acceptable for personal use by the owner, but it is not a B2B posture and not safe for untrusted repos/content. The next-cycle move is a sandbox boundary with secrets outside and egress allowlisted, starting with the cheapest $0 local option (§5, item 6). Note the argument-injection lesson: Piplet's approval/allowlist checks must validate full argument vectors, not command names.

## 2. Research papers and approaches

Summaries below are in my own words. Each entry gives title, authors/year, venue, and a link. Papers marked `[abstract/secondary]` were summarised from the abstract and/or secondary explainers, not a full read — verify any claim before citing it in a deck or paper. ArXiv IDs are given where the cited source supplied them; where I rely on the commonly cited ID, that is noted.

### 2.1 Agent memory: episodic, semantic, and procedural — keep them separate

The field borrows its vocabulary from cognitive science. A Sept 2023 Princeton framework ("Cognitive Architectures for Language Agents", Sumers et al.) splits agent memory into **working memory** (current context), **episodic memory** (records of past events), **semantic memory** (facts about the world/user), and **procedural memory** (how to do things, held in code or instructions). Most 2023–2026 systems are variations on how to store, retrieve, consolidate, and forget across those four. [secondary — timeline at https://ppc.land/agent-memory/]

1. **"Generative Agents: Interactive Simulacra of Human Behavior" — Park et al., 2023, UIST 2023 (arXiv:2304.03442).** [abstract/secondary] Twenty-five simulated characters in a small town, each keeping a *memory stream* of natural-language observations. Retrieval scores each memory by recency, importance, and relevance; the agent periodically condenses observations into higher-level "reflections" that guide future behaviour. The pattern to steal: store raw observations, retrieve by a combined score, and summarise upward on a schedule — not just "keep the last N messages." Link: https://arxiv.org/abs/2304.03442 (commonly cited ID; abstract confirmed via secondary summaries in this sweep).
2. **"MemGPT: Towards LLMs as Operating Systems" — Packer et al., 2023, arXiv:2310.08560.** [abstract/secondary] Treats the context window as main memory and external storage as disk: the model pages information in and out with explicit tools, managing a queue, working memory, and long-term recall itself. The ancestor of Letta (§1.4). The pattern to steal: the agent should *manage* its own memory with tools (read/write/archive/forget), not have the harness silently truncate history. Link: https://arxiv.org/abs/2310.08560 (ID supplied in a cited ICML 2026 paper's references, https://raw.githubusercontent.com/mlresearch/v306/main/assets/wang26ee/wang26ee.pdf).
3. **"Cognitive Architectures for Language Agents" — Sumers et al., 2023, arXiv (Sept 2023).** [secondary] The taxonomy paper: working/episodic/semantic/procedural memory, plus decision procedures. Useful as a design checklist — ask, for each memory Piplet keeps, which of the four it is and what its retention/forgetting rule is. Link: search arXiv for the title; no direct link verified in this sweep.
4. **"Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory" — Chhikara et al., 2025, arXiv:2504.19413 (28 Apr 2025), ECAI 2025.** [abstract/secondary] The Mem0 paper: an LLM distils conversations into short fact-like memories, stored with embeddings and retrieved per user/agent/run; reports +26% accuracy over a naive baseline and large latency/token savings vs full-context on LoCoMo. Treat the numbers as vendor-reported (see the methodology disputes in §1.4). The pattern to steal: extraction + deduplication + scoped retrieval, with a pruning job for stale facts. Link: https://arxiv.org/abs/2504.19413 (ID supplied in the Mem0 repo survey, https://lucagattoni.github.io/knowledge-graph-tutorial/kb-kg/projects/mem0/).
5. **A-Mem (2025), MemoryOS (Kang et al., 2025), Zep/Graphiti (temporal graph).** [secondary] A family of 2024–25 systems that organise memories as graphs (entities + relations + timestamps) or OS-style tiers, so that contradictions and time can be reasoned about instead of overwritten. The pattern to steal: timestamp every fact; never silently overwrite a contradicted fact — keep both, mark the newer one current, and surface the conflict when it matters. No single primary link verified in this sweep; see the GAM paper's related-work section (below) for the lineage.
6. **"GAM: Hierarchical Graph-based Agentic Memory for LLM Agents" — 2026, arXiv:2604.12285.** [abstract read] Proposes decoupling memory *encoding* from *consolidation*: ongoing dialogue lives in an isolated event-progression graph (episodic buffering), and is integrated into a global topic-associative network only when a semantic shift is detected, minimising interference while preserving long-term consistency. Evaluated on LoCoMo and LongDialQA against state-of-the-art baselines. The pattern to steal: don't consolidate on every turn — buffer the episode, consolidate at boundaries. Link: https://arxiv.org/html/2604.12285.
7. **"E-mem: Multi-Agent Based Episodic Context Reconstruction for LLM Agent Memory" — Wang et al., ICML 2026, arXiv:2601.21714.** [abstract/secondary] Argues that compressing history into embeddings/graphs *destroys* the sequential context needed for deep reasoning. Instead: keep raw context uncompressed, split across small-model assistant agents, each guarding one segment; a master agent plans globally and activates assistants via multi-path retrieval. Reports >54% F1 on LoCoMo, +7.75 over GAM, with ~70% fewer tokens (paper-note summary). The pattern to steal — at Piplet's scale, the *cheap* version: keep verbatim episode text in SQLite and retrieve whole episodes, not just extracted facts, when the task needs sequence (e.g. "what did we decide, in what order?"). Links: https://en.papernotes.org/ICML2026/llm_agent/e-mem_multi-agent_based_episodic_context_reconstruction_for_llm_agent_memory/ (paper note, ICML 2026); full paper PDF: https://raw.githubusercontent.com/mlresearch/v306/main/assets/wang26ee/wang26ee.pdf.
8. **"Voyager: An Open-Ended Embodied Agent with Large Language Models" — Wang et al., 2023, arXiv:2305.16291.** [secondary] A Minecraft agent that writes code skills, revises them from environment feedback and execution errors, self-verifies them, and stores verified programs in a *skill library* for later retrieval and reuse. The pattern to steal: a skill is only "learned" after it has *worked* — verification before storage. This is the research ancestor of the Hermes Curator pattern and of Piplet's proposed human-reviewed skill writer. Link: https://arxiv.org/abs/2305.16291 (commonly cited ID).
9. **"ChatDB: Augmenting LLMs with Databases as Their Symbolic Memory" — Hu et al., 2023, arXiv.** [secondary, cited in E-mem references] Uses a database as explicit symbolic memory the model queries with SQL-like operations, rather than relying on fuzzy vector recall for exact facts. The pattern to steal: some memories (dates, amounts, IDs, preferences) belong in structured tables with exact lookup, not embeddings. Piplet's SQLite is already the right substrate — use it as memory, not just as a log.

**Memory benchmarks to know:** **LoCoMo** (Maharana et al., 2024) — long conversations with multi-hop, temporal, and adversarial questions; the standard long-conversation memory benchmark. **LongMemEval** — long-term memory evaluation; **LongDialQA** — long-dialogue QA. **MemoryAgentBench** — a newer agent-memory benchmark cited in 2026 comparisons. Scores across these are not comparable across papers unless the harness, reader model, and memory budget are identical — always read the method, not just the headline.

### 2.2 Tool-use reliability: small errors compound; the harness must do the reliability work

1. **"Toolformer: Language Models Can Teach Themselves to Use Tools" — Schick et al., 2023, NeurIPS 2023 (arXiv:2302.04761).** [secondary] A 6.7B GPT-J model proposes API calls inside ordinary text, executes them, and keeps only the calls that measurably lower its own next-token loss on the following text — a self-supervised filter with no human labels. It learns *when* to reach for a calculator, search engine, translator, QA system, or calendar, not just how. The lesson for Piplet is conceptual, not implementational: tool-use judgment (when *not* to call a tool) matters as much as tool-use syntax, and it can be learned from outcome signals rather than hand-written rules. Piplet should not fine-tune a Toolformer — it should use native function calling (§1, prior cycle) and spend its effort on validation, budgets, and retry policy. Link: https://arxiv.org/abs/2302.04761 (commonly cited ID); explainer: https://agent-atlas.blackarcindustrial.com/papers/toolformer-language-models-can-teach-themselves-to-use-tools/.
2. **"Gorilla: Large Language Model Connected with Massive APIs" — Patil et al., 2023, arXiv:2305.15334; NeurIPS 2024.** [secondary] When asked to call one of thousands of APIs, general models invent APIs that don't exist or use real ones wrong. Gorilla fine-tunes LLaMA-7B on APIBench (1,645 ML API calls) with *retriever-aware training* — relevant API docs in the prompt, so the model can follow updated docs at test time — and evaluates with AST matching that separately counts *hallucinated* calls (calls matching no real API). It beat GPT-4 by 20.43% and ChatGPT by 10.75% on API-call accuracy in the zero-shot setting, with far less hallucination. The work led directly to the Berkeley Function Calling Leaderboard. The patterns to steal: (a) measure hallucinated-tool-calls separately from wrong-argument errors; (b) retrieve tool docs into context instead of stuffing every tool definition into every prompt (progressive disclosure again); (c) a small specialised model can beat a large general one on *accurate* calling. Link: https://arxiv.org/abs/2305.15334 (commonly cited ID); review: https://www.chriswirz.com/reviews/gorilla-large-language-model-connected-with-massive-apis/index.html.
3. **"ToolLLM: Facilitating Large Language Models to Master 16,000+ Real-world APIs" / ToolBench — Qin et al., 2023, ICLR 2024 (arXiv:2307.16789).** [secondary] Scales tool-use training and evaluation to 16k+ real APIs, with a focus on tool *selection* across a large catalogue, not just execution of a known tool. The lesson: as Piplet's tool count grows past ~5–10, selection becomes the failure mode — which is why tool retrieval/disclosure and small per-task tool subsets matter more than adding tools. Link: https://arxiv.org/abs/2307.16789 (commonly cited ID).
4. **"Augmenting Language Models with Tools: A Survey" — Mialon et al., 2023, arXiv.** [secondary] Survey finding cited in explainers: tool use improved factual accuracy, mathematical reasoning, and real-world information tasks by 20–50% vs base models. Useful as background, not as a Piplet design input.
5. **The compounding-reliability arithmetic (practitioner summary, 2026).** If each step is 90% reliable, a 10-step task is ~35% reliable end-to-end; a 20-step task ~12%. Every additional tool hop multiplies failure. The mitigations are harness-side, not model-side: validate every call against its schema before executing; verify every result (did the action actually happen?); retry with a different approach, not the same call; keep plans short; checkpoint so a failure resumes instead of restarting. Explainer: https://journeyofadistractedmind.com/tool-use-in-llms (2026). Evolution survey: https://hyacehila.github.io/en/blog/2026/03/05/llm-tool-use-evolution/ (5 Mar 2026).

### 2.3 Planning and self-correction: interleave, plan-first, or search — and correct only on outside evidence

1. **"ReAct: Synergizing Reasoning and Acting in Language Models" — Yao et al., 2022 (arXiv 6 Oct 2022), ICLR 2023 (arXiv:2210.03629).** [secondary] Interleave a written *Thought* with each *Action* (tool call), then read the real *Observation* before the next thought. With one or two in-context examples, the paper reports absolute success gains of 34 points on ALFWorld and 10 points on WebShop over imitation/RL baselines, and reduced hallucination/error propagation on HotpotQA and FEVER vs chain-of-thought alone. The critical implementation detail: cut generation at "Observation:" (stop sequence) so the *runtime* supplies real data instead of the model hallucinating it. Failure modes to guard: infinite loops, hallucinated success from silent tool returns, context overflow. Link: https://arxiv.org/abs/2210.03629 (commonly cited ID); explainers: https://safeguard.sh/resources/blog/ai-agent-planning-patterns-explained-react-plan-and-execute-and-reflection (Oct 2026); https://www.arunbaby.com/ai-agents/0014-react-pattern-deep-dive/ (Nov 2026).
2. **"Reflexion: Language Agents with Verbal Reinforcement Learning" — Shinn et al., 2023, NeurIPS 2023 (arXiv:2303.11366).** [secondary] Adds a critic step: an external evaluator (unit tests, environment success signal, heuristic) decides whether an attempt failed; the model writes the *cause* as a verbal reflection; the reflection is stored in an episodic buffer and added to the next attempt's prompt. With external feedback it reached 91% pass@1 on HumanEval (vs an 80% GPT-4 baseline in the paper). The key qualifier: Reflexion works *because* the signal comes from outside the model. Link: https://arxiv.org/abs/2303.11366 (commonly cited ID).
3. **"Self-Refine: Iterative Refinement with Self-Feedback" — Madaan et al., 2023, NeurIPS 2023 (arXiv:2303.17651).** [secondary] One model acts as generator, feedback provider, and refiner, with no extra training or external data; reports ~20 points average absolute improvement across 7 tasks. Weaker evidence than Reflexion because the feedback is self-generated.
4. **"Large Language Models Cannot Self-Correct Reasoning Yet" — Huang et al., 2023, ICLR 2024 (arXiv:2310.01798).** [secondary] The essential counterweight: without external feedback, models struggle to self-correct reasoning and sometimes get *worse*. Self-generated tests can pass on wrong code (noted in Reflexion's own analysis). **Piplet rule: retry/correction loops must be gated on external signals** — tests, validators, tool errors, search results, file/state diffs — never on the model's own opinion that it did well. Link: https://arxiv.org/abs/2310.01798 (commonly cited ID).
5. **Plan-and-execute family: Plan-and-Solve (Wang et al., May 2023), ReWOO (Xu et al., May 2023), LLMCompiler (Dec 2023).** [secondary] Separate a planner from an executor: the planner writes the whole plan of tool calls (with placeholders) up front, workers fill in results, a solver combines them. ReWOO reported ~5× token efficiency and ~4 points higher accuracy on HotpotQA than interleaved methods; LLMCompiler reported up to 3.7× lower latency and 6.7× lower cost than ReAct. The trade-off: plan-first is cheaper and more predictable for predictable work, but interleaved ReAct adapts better when each step depends on the last result (debugging, web tasks). Piplet should support both: plan-first for routine/known workflows, ReAct for exploratory ones, with re-planning on failure. Explainer: https://aimap.page/en/learn/agents/planning-memory/ (Nov 2026).
6. **"Tree of Thoughts: Deliberate Problem Solving with Large Language Models" — Yao et al., 2023, NeurIPS 2023 (arXiv:2305.10601).** [secondary] Generate several candidate thoughts, evaluate how promising each is, and search (breadth/depth-first) with backtracking. Powerful for puzzles and search-heavy tasks; expensive in tokens. Not a default for Piplet — reserve for genuinely branching problems.
7. **CRITIC (Gou et al., 2023).** [secondary] Self-correction grounded in external tools (search engines, code interpreters) that verify and revise outputs. Same lesson as Reflexion: the verifier must be outside the model.

### 2.4 Multilingual approaches: translation is not understanding, and code-mixing is the real test

1. **"IndicTrans2: Towards High-Quality and Accessible Machine Translation Models for all 22 Scheduled Indian Languages" — Gala et al., 2023, Transactions on Machine Learning Research (Dec 2023), arXiv:2305.16307.** [abstract/paper read via PDF] Before this work there was no parallel training data spanning all 22 scheduled languages, no robust benchmark covering them, and no translation model supporting all 22. Contributions: the Bharat Parallel Corpus Collection (BPCC, 230M bitext pairs, 126M newly added incl. 644K manually translated pairs); the first n-way parallel benchmark covering all 22 languages (IN22, incl. conversational sets); and IndicTrans2 (1.1B parameters, distilled ~211M versions), the first model supporting all 22, with direct Indic↔Indic translation (462 directions) without passing through English. Models and data released under permissive licences (MIT, per repo notes; long-context RoPE update 18 Jan 2025). The pattern to steal: script unification where feasible (lexical sharing across languages), and conversational benchmarks — not just formal text. Links: https://storage.googleapis.com/arxiv-dataset/arxiv/arxiv/pdf/2305/2305.16307v3.pdf (paper PDF); repo summary: https://awesome.ecosyste.ms/projects/github.com%2FAI4Bharat%2FIndicTrans2.
2. **Conversational domain adaptation of IndicTrans2 (Singh, June 2026, arXiv:2606.29024).** [abstract read] Adapting IndicTrans2-1B to conversational register across 21 Indic languages using only public data (OpenSubtitles, BPCC-H-Daily, Tatoeba). Plain fine-tuning improved conversational chrF but forgot the general domain (−3.9 chrF on FLORES for Hindi); mixing general data back in (experience replay) + averaging fine-tuned weights with the base (model souping) removed the trade-off (+6.2 mean conversational chrF, FLORES unchanged). Honestly reported: a blind human + multi-model LLM check did *not* confirm the chrF gains as perceived quality improvement — the gain is largely register match to references. Lesson: automatic metrics overstate conversational quality; human checks are the gate. Santali, Sanskrit, Kashmiri, Bodo stay low after adaptation. Link: https://arxiv.org/html/2606.29024.
3. **"Assessing Translation Capabilities of Large Language Models involving English and Indian Languages" — Mujadia et al., IIIT Hyderabad, 2023, arXiv:2311.09216.** [abstract read] Compares raw LLMs, in-context learning, LoRA fine-tuning, and full fine-tuning for English↔22 Indian languages against IndicTrans2, Google Translate, and SeamlessM4T. Two-stage fine-tuned LLaMA-13B is the best LLM-based system in the study, but the gap to dedicated translation systems and the variance across languages underline that a general LLM is not automatically a good Indic translator. Link: https://arxiv.org/pdf/2311.09216.
4. **Code-mixing research (general finding, §4 for UX detail).** Linguistic work distinguishes inter-sentential switching (language changes at sentence boundaries) from intra-sentential switching (mixing inside one sentence, usually with one language's grammar as the frame — in Hinglish, Hindi grammar + English nouns/phrases: "appointment cancel kar do"). Systems that force input into one language too early, or treat transliteration as cosmetic cleanup, fail on real Indian speech/text. See §4 for the applied patterns and sources.

### 2.5 Agent evaluation and benchmarks: score trajectories, not single turns

The 2024–2026 consensus across practitioner guides: agent eval must score multi-step *trajectories* (success-at-N, partial credit, final-state checks), because errors compound, partial progress matters, and a model that scores well on chat benchmarks can fail as an agent if it cannot recover from tool errors or maintain state. Public benchmark scores typically diverge from production performance — teams should eval against their own task distribution and guard against contamination. Tool outputs are stochastic (network, APIs, environment), so evals must sandbox or mock tool calls consistently. [secondary]

**Piplet implication:** Piplet does not need to run SWE-bench. It needs (a) a small golden set of *its own* tasks (personal workflows + the one B2B workflow), (b) trajectory scoring (did each step's tool call match the expected call? did the final state match? how many retries? what did it cost?), and (c) a regression run before every release and after every model change. That is backlog item #1, and it is the highest-value item in this file.

## 3. What B2B automation buyers and investors publicly say they want

No one was contacted for this section. All findings are from public blog posts, docs, talks summaries, and procurement guidance. Vendor blogs are labelled as interested sources; procurement/legal guidance is labelled as such. Nothing here is legal advice.

### 3.1 The buyer checklist has stabilised — and it is about governance, not demos

By mid-2026, enterprise buyers treat AI agents as *not ordinary SaaS*. A July 2026 research synthesis of buyer-side governance reports procurement checklists routinely demanding: kill switches, evidentiary audit trails, human-in-the-loop boundaries, model change control, outcome-based SLAs, and ISO/IEC 42001 or SOC 2 attestations as *gating* conditions. Law firms (Mayer Brown, Clifford Chance, cited therein) argue legacy SaaS paper cannot carry agentic risk. Reference frameworks have consolidated around ISO/IEC 42001, the NIST AI Risk Management Framework + Generative AI Profile (AI 600-1), the EU AI Act, and Singapore IMDA's Model AI Governance Framework for Agentic AI (updated May 2026). The Cloud Security Alliance's AI Controls Matrix assigns ~243 controls across four supply-chain layers. Large vendors responded by productising governance itself (ServiceNow AI Control Tower, Microsoft Agent Governance Toolkit). [secondary — research synthesis, 2 July 2026]

- Source: https://zylos.ai/research/2026-07-02-buyer-side-governance-enterprise-ai-agent-deployments/

**The specific asks, distilled across four public sources (July–Oct 2026):**

1. **Kill switch / emergency stop.** A headline item. EU AI Act Art. 14 (human oversight, including a stop mechanism); ServiceNow added agent kill switches to AI Control Tower in May 2026. Piplet already has freeze — the B2B version needs a *per-client, per-workflow* stop that a non-technical buyer can hit, plus proof it worked. Sources: Zylos (above); https://grow.cleverbridge.com/blog/agentic-ai-b2b-saas-human-approval (5 Oct 2025, updated 21 Apr 2026) — "Week 0: ship with a kill switch, audit logs, and rollback."
2. **Audit trails and evidentiary logging.** Converging on append-only, hash-chained logs and OpenTelemetry-style per-step tracing tagged with agent ID and model version, satisfying SOC 2 CC7.2 and EU AI Act Art. 12 (minimum log retention for high-risk systems) simultaneously. Procurement teams and insurers reportedly request audit-trail *demos* before signing larger contracts. For regulated workflows, buyers want to trace any output back to its source information and workflow steps — "the AI said so" is not an explanation. Sources: Zylos (above); https://www.deepknit.ai/blog/buyers-ask-approving-ai-regulated-workflows/ (Nov 2026).
3. **Human-in-the-loop boundaries, tiered by risk.** Tiered autonomy is the norm: read-only / reversible / external-facing / high-risk-irreversible, with mandatory human approval only at the top tier and escalation on uncertainty. Buyers no longer accept a yes/no on human review — they want to know *which* actions need sign-off, which are logged for after-the-fact review, and which the agent executes alone. "Most enterprise buyers are not searching for fully autonomous AI. They are searching for controlled automation." (DeepKnits, Nov 2026.) The Cleverbridge piece adds the operating rule: *never widen autonomy without evidence* — passing evals, guardrail coverage, safe rollback, alerting — and the north star of moving from human-in-the-loop to human-*above*-the-loop only when metrics justify it (e.g. consequential-action detector recall ≥95%, approval-rework rate <10%). Sources: Zylos; DeepKnits; Cleverbridge (above).
4. **Evals as acceptance, not UAT.** Acceptance for non-deterministic agents is being redefined as statistical tolerance bands — golden datasets, failure budgets, workflow success-rate KPIs — rather than deterministic pass/fail UAT, with re-acceptance rights after model updates emerging as a standard ask. A weekly eval against a frozen test set is described as cheap insurance vs catching a regression from a support ticket. Model-version ownership is a procurement question: who owns the version running, what notice applies on deprecation (OpenAI: ≥6 months for GA models, 3 months specialised, 2 weeks preview; Anthropic: ≥60 days for public models — as reported Oct 2026), and what happens when a provider pushes an update nobody downstream asked for. Sources: Zylos; https://mylocal.io/2026/10/21/five-decisions-your-ai-pilot-needs-before-procurement-review/ (21 Oct 2026).
5. **Security: prompt-injection detection, data handling, vendor posture.** Buyers ask who sees prompts, how injection attempts are detected, what happens when a human disagrees with an agent action, and what the vendor does on model updates. The fast-moving teams ship a short AI fact sheet *alongside* SOC 2 instead of waiting for the 140-question questionnaire. Prompt retention/redaction, where inference runs, what logs the buyer's SIEM can pull, and injection resistance folded into the regression suite (not tested once at launch) are all named. Source: MyLocal (above).
6. **Integration realism.** Each connected system (CRM, calendar, email, Slack) adds 2–5 days of build work in agency pricing guides; 3–5 integrations add $1,000–2,000, 6–10 add $2,000–5,000, 10+ means a platform, not a script (see §3.3). Buyers want named integrations with named failure behaviour, not "connects to everything."
7. **The "last mile" problem.** Agents shine in demos and fail on the last mile, where small mistakes carry dollar impact (a hallucinated discount, fictional campaign, misapplied tax). The Cleverbridge piece's case study: in Apr 2025 a Cursor AI agent confidently told users of a non-existent single-device-per-subscription policy, generalising from training data instead of a verified source of truth. The fix pattern: verified sources of truth, diffs/checklists/one-click approvals for review, and humans as *error analysts* who categorise failures in weeks 1–2 (100% review) before autonomy widens. Source: Cleverbridge (above).

**What this means for a solo founder selling to small businesses (not enterprises):** an SMB buyer will not send a 140-question questionnaire — but they will ask the same questions in plain language ("can I stop it?", "can I see what it did?", "who approves a message before it goes out?", "what happens if it's wrong?"). The artefacts that answer those questions — kill switch, audit log, approval tiers, eval numbers on *their* workflow, a one-page AI fact sheet — are the same artefacts, just smaller. Build them once for Piplet's own use, and they become the B2B sales pack.

## 4. Multilingual UX patterns for Indian users

### 4.1 The core fact: code-mixing is normal speech, not an edge case

Real Indian users switch languages mid-sentence, mid-word, and mid-conversation — and they do it skilfully, following patterns, not at random. A Hindi voice agent that does well in demos loses accuracy in production because real calls don't sound like clean training audio: speakers switch between Hindi and English mid-sentence, pronounce English brand names with local accents, stretch vowels, clip consonants, speak over background noise, and interrupt prompts before the turn ends (Exotel, Sept–Oct 2026). Example utterances from public guides: "Mera card block ho gaya, but app mein active dikh raha hai" (intent, entities, and language boundaries all shift inside one utterance); "Mera order abhi tak deliver nahi hua, can you check the status?"; "appointment cancel kar do"; "EMI ka date change ho sakta hai?"

Linguists distinguish **inter-sentential** switching (full sentence in one language, then a full sentence in another) from **intra-sentential** switching (mixing inside one sentence — the harder case for machines). In everyday Hinglish the grammatical frame ("matrix language") is usually Hindi and the inserted content ("embedded language") is English: nouns like *appointment*, *balance*, *delivery*, plus fixed phrases like *no problem* / *please confirm*. The English noun stays English, but the verb, postposition, and word order follow Hindi. The Hindi:English ratio shifts by person, city, topic, and mood — a caller may be nearly all-English about banking and nearly all-Hindi about family — and formal calls drift toward English vocabulary while casual ones drift toward Hindi, sometimes mid-call. The same patterns repeat across India: Tanglish (Tamil+English), Tenglish (Telugu+English), Banglish, Minglish (Marathi), Kanglish (Kannada), Manglish (Malayalam), Gujlish, Punglish — plus mixes of two Indian languages, and callers who start in Hindi, drop an English number, and finish in Bhojpuri in one sentence.

- Sources: https://exotel.com/blog/hindi-voice-agent/ (Sept–Oct 2026); https://vaami.ai/blog/hinglish-voice-ai-code-switching-guide (1 Oct 2026); https://www.voxindia.ai/languages (2026, 12-language code-switch coverage incl. Hinglish/Tanglish/Tenglish/Banglish/Minglish/Kanglish/Manglish/Gujlish/Punglish); https://www.omnilingo.us/en/learn/code-mixing-hinglish-and-friends (2026); https://www.callmangal.com/blog/multilingual-ai-voice-agents-india-hindi-hinglish (2026).

### 4.2 UX patterns that follow from that fact (text + voice)

1. **Don't force a language or script choice.** "Do not force users to pick one language or script. Let them write the way they talk." (OmniLingo, 2026.) A language menu that must be picked before speaking/typing is a failure mode. Accept mixed input as normal; detect per-utterance, not per-user, and re-detect as the conversation shifts.
2. **Reply in the language and script the user used — or let them choose, and test that the model does it.** If the user writes Romanised Hindi ("kal subah aana"), replying in Devanagari — or in formal translated Hindi — can feel wrong even when it is "correct." Keep familiar English terms inside Indian-language replies (EMI, UPI, KYC, delivery, appointment): automatically translating every familiar English term into formal Hindi makes a conversation sound *less* natural, not more (CallMangal, 2026). Decide the transcript/script policy explicitly: the same sentence can be written in Roman script or Devanagari, and downstream NLU must handle both.
3. **Don't force every transcript into one language too early, and don't treat transliteration as cosmetic cleanup.** (Exotel, 2026.) Hinglish turns get split badly, English terms get transliterated inconsistently, and mixed-script outputs become hard for downstream understanding to parse. Keep the original text; normalise only a *copy* for matching/search. Normalisation rules that destroy meaning: lowercasing merging a name with a common word; stripping emoji that carries emotion a support team needs; mapping spelling variants ("nahi"/"nhi"/"nehi") without a speaker-checked list. Unicode NFC matters for Indic scripts (a letter with nukta can be stored two ways; NFC makes both forms the same). Remove punctuation by Unicode category so Indic vowel signs survive. (OmniLingo, 2026.)
4. **Design the whole speech stack as one system, not an ASR tuning task.** Telephony, streaming, ASR, NLU, TTS, routing, and human handoff share context and latency budget. Don't clip the first 200–400ms of live speech (intent-bearing words live there). Handle interruptions (barge-in), background noise, 8 kHz phone audio (a common production scenario for Indian voice apps, per Sarvam docs via CallMangal), fast/slow/soft/stressed speech, and older voices. Build a representative test-audio library: metro + non-metro speech, varied English insertions, domain vocabulary *in natural sentences* (EMI, loan number, premium, policy, UPI, card, mandate, statement, due date, KYC), male + female + older voices. Do not validate with one "neutral Hindi" speaker set. (Exotel, 2026.)
5. **Test end-to-end task completion, not component accuracy.** A 2026 research preprint evaluating a Hindi voice agent (3,760 multi-turn tests across 960 simulated calls, cited by CallMangal) found performance on individual components did not reliably predict successful end-to-end task completion. The Vaami guide offers a 10-point protocol to run on any vendor with your own audio. Piplet's version: a 20-phrase code-mixed test set (OmniLingo's suggested exercise) + end-to-end task tests in Hinglish/Tenglish, run before every release that touches language handling.
6. **Numbers, names, and entities need explicit handling.** Spoken-number conversion, entity standardisation, Romanised-Hindi cleanup, mixed-language formatting, and punctuation recovery are named as required post-ASR steps (Exotel). English brand/product names pronounced with local accents must resolve to the same entity. Dates, amounts (₹), phone numbers, and order IDs must survive transcription in a parseable form — confirm them back to the user in the user's own script before acting on them.
7. **Define a safe recovery path and a human handoff.** Good multilingual voice design assumes failure: when confidence is low or the language shifts unexpectedly, confirm, rephrase, offer the choice ("Hindi mein baat karein ya English?"), and hand off cleanly with context — never loop the same prompt. (CallMangal, 2026.)
8. **Voice-first, low-bandwidth, WhatsApp-shaped.** Voice interfaces matter most for users with limited digital literacy or who prefer speaking to navigating apps. BHASHINI/BharatGen-era public infrastructure is explicitly voice-first and multilingual (§4.3). For SMB B2B, the channel is often WhatsApp + phone + email, on low bandwidth — design for short turns, voice notes, and text that works on a small screen in mixed script. Keep replies short; confirm before acting; show what will happen in the user's language before doing it.
9. **Register matters.** Formal calls drift to English vocabulary; casual ones to Hindi. A single caller moves along that range mid-call. Don't lock a "language" per user — track register per turn, and mirror it. Don't "correct" the user's mixing; it is skilled bilingual behaviour, not an error.

## 5. Ranked backlog for NEXT cycles

**Ranking rule:** real value for a solo student-founder building a personal AI first and B2B automation second, at $0, with limited time — weighted toward (1) trust/evidence a buyer or user can check, (2) compounding (gets better with use), (3) unblocking the next item, (4) low ongoing cost. **Excluded from ranking (already in flight this cycle):** multilingual UI, new deny-first tools, UX polish — items below extend them, they don't duplicate them.

**$0 cost check key:** `$0` = no new spend (local compute / existing free tiers only, within published limits — re-check limits at build time). `$0*` = $0 if kept inside a stated free tier / local-only; needs a quota guard. `VERIFY` = cost/licence must be confirmed before building.

### #1 — Eval harness + golden task set + regression runs [HIGHEST VALUE]

- **What:** A local eval runner (Node script + SQLite results) that runs Piplet end-to-end on a frozen golden set of ~20–30 tasks (personal workflows + the one B2B workflow + 20 code-mixed Hinglish/Tenglish phrases + tool-call correctness cases), scores *trajectories* (expected tool call + args? final state correct? retries? cost/latency?), and reports pass rate + cost per task. Run before every release and after every model/provider change. Include BFCL-style checks (AST/arg match, hallucinated-tool-call counted separately) and τ²-style pass^k (same task N times — consistency matters more than a single lucky pass).
- **Why:** Every other item in this file depends on knowing whether a change helped or hurt. Buyers accept statistical tolerance bands + golden datasets, not demos (§3.1). Anthropic's own advice is "build a small end-to-end eval" before restructuring agents (§1.3). Without this, Piplet cannot honestly claim reliability, widen autonomy, or price outcomes.
- **What it replaces:** Ad-hoc manual testing + unit tests only (131/131 unit tests prove components, not trajectories). It does not replace unit tests — it sits above them.
- **$0 check:** $0. Local runner; golden tasks run against mocked tools + a small live subset within existing free tiers. Add a per-run token/step budget so an eval can't burn a day's quota.
- **Evidence gate:** Golden set committed; first baseline run recorded with pass rate + cost; a deliberate regression (e.g. break one tool schema) is caught by the harness before merge.
- **Risks:** Golden-set overfitting (rotate in fresh tasks monthly; keep a held-out set); judge variance (score by final state + tool-call match, not by an LLM judge, wherever possible).

### #2 — Hash-chained audit log + run receipts + tiered autonomy + per-workflow kill switch

- **What:** Extend the existing `audit_log` + freeze into: (a) append-only, hash-chained log entries (each entry hashes the previous — tamper-evident), tagged with agent/run ID, model + version, tool, full args, result shape, and approval decision; (b) a human-readable *receipt* per run (what was requested, what was done, what was approved, what failed, cost) exportable as JSON/Markdown; (c) four autonomy tiers — read-only / reversible / external-facing / high-risk-irreversible — with approval required at the top tiers and escalation on low confidence; (d) freeze extended to per-workflow/per-client stop with proof-of-stop in the log.
- **Why:** This is the B2B gating artefact (§3.1: kill switches, evidentiary trails, HITL boundaries are procurement gates; insurers/procurement request audit-trail demos). It also protects Ankush personally: every automated action is explainable after the fact.
- **What it replaces:** The current flat `audit_log` (kept as the substrate — this adds chaining, receipts, and tiers on top). It replaces "trust me, it worked" with checkable evidence.
- **$0 check:** $0. SQLite + Node crypto (built-in). Log retention: define it (e.g. 1 year minimum per DPDP summaries — VERIFY against the Rules text; personal-use logs can be shorter with user control).
- **Evidence gate:** Tamper test (modify one historical entry → chain verification fails); receipt export reviewed by a non-technical reader for comprehensibility; freeze test per workflow.
- **Risks:** Log bloat (cap entry size; store large tool outputs by reference); secrets in logs (reuse the existing key-refusal/redaction rules — never log keys, tokens, or full PII).

### #3 — Skills system: curated SKILL.md + progressive disclosure + human-reviewed curator

- **What:** Formalise `skills/` as Agent-Skills-style folders (`SKILL.md` with name/description frontmatter + instructions + optional scripts). The brain sees only short descriptions; full skill content loads only when the task matches (progressive disclosure). Add a nightly/weekly *curator draft* job (Hermes pattern): read recent successful runs from SQLite, draft *one* Markdown skill per workflow with evidence (run IDs) cited — landing as a **draft for human approval**, never auto-applied, never touching `permissions.json` or the allowlist. Include the multilingual reply-mirroring rules (§4.2) and the eval/approval checklists as the first skills.
- **Why:** Anthropic's Oct 2026 finding: a single agent with skills frequently beat subagent designs on quality, cost, and latency (§1.3). SkillsBench: curated human-written skills +16.2pp; self-generated skills slightly negative. Skills compound: Piplet gets better at Ankush's actual workflows instead of starting from zero daily. Cheapest capability multiplier available — no new infra, no new model.
- **What it replaces:** Ad-hoc prompt stuffing (everything in every prompt) and any temptation to build a multi-agent sprawl. It replaces nothing already built — it organises `skills/` (currently `coding-agent.md`, `goose.md`) into a load-on-demand system.
- **$0 check:** $0. Markdown + SQLite + existing brain calls (Flash-Lite for drafts).
- **Evidence gate:** Eval harness (§#1) shows no regression and lower tokens/turn after folding a skill in; a learned skill that contradicts an existing rule is flagged, not merged (test this case explicitly).
- **Risks:** Skill drift / prompt injection via third-party skills (never auto-install; review every skill; treat skill content as untrusted input when it comes from outside — see ClawHub/ToxicSkills findings, §1.1/§1.3).

### #4 — Memory v2: sqlite-vec recall + timestamped facts + contradiction handling + user forget/edit

- **What:** (a) sqlite-vec `vec0` table in the existing SQLite file + local embeddings (e.g. FastEmbed `all-MiniLM-L6-v2`, ONNX, no GPU) + FTS5 keyword search fused in SQL; a `recall(query)` step before each brain turn injects the top 3–5 memories. (b) Fact store with timestamps, source (which conversation/run), and scope (user/session); contradictions kept visible (newer marked current, older kept, conflict surfaced when relevant) — the Zep/Graphiti lesson without the graph cost. (c) Episode buffering: keep verbatim episode text; consolidate into facts only at episode boundaries (GAM pattern, §2.1). (d) User-visible memory UI: view, edit, delete/forget any fact; export. (e) A pruning job for stale facts (mem0's add-only lesson).
- **Why:** Piplet today has notes + raw history only; retrieval is the difference between an assistant and a chatbot. Timestamped, contradiction-aware memory is what makes long-term use trustworthy ("you told me X last week, Y today — which stands?"). Local-first keeps it $0 and private.
- **What it replaces:** Flat Markdown notes + full-history stuffing. Defers mem0 self-hosted until/unless extraction quality is needed (prior cycle's verdict stands).
- **$0 check:** $0. `sqlite-vec` (Apache-2.0/MIT, pin stable `0.1.9`, not alpha), local ONNX embeddings. VERIFY sqlite-vec's current release status at build time (last push May 2026 per the prior cycle).
- **Evidence gate:** LoCoMo-style spot checks on Piplet's own conversations (recall the right fact, resolve a contradiction correctly, forget on request and prove it); memory cost (tokens/turn) tracked, not just recall.
- **Risks:** Stale/wrong facts presented confidently (always show source + date with recalled facts in the UI); embedding-model drift (pin the model; re-embed on change); pre-v1 sqlite-vec breaking changes (pin version, keep the FTS5 fallback working without vectors).

### #5 — MCP client (deny-first) + MCP server exposing Piplet's tools

- **What:** (a) An MCP *client* in Piplet that can consume MCP servers (starting with Playwright MCP for browser-via-accessibility-tree, no vision tokens) behind the *same* deny-first rules as native tools: allowlisted servers only, per-tool approval tiers, schema validation, call budgets, audit logging, no autonomous server installation. (b) An MCP *server* exposing Piplet's own allowlisted tools with the same rules, so other MCP clients (editors, other agents) can use Piplet safely. Layer on the production requirements MCP itself omits: auth, sandboxing (§#6), budgets, logging (§#2).
- **Why:** MCP is the standard plug (§1.3); every framework consumes it, so tools built behind it survive framework switches. It turns "one bespoke integration per tool" into "one protocol." The security literature is explicit that MCP without these layers is unsafe — Piplet's deny-first posture is the layer.
- **What it replaces:** Bespoke per-tool glue for each new integration. It does not replace the native function-calling loop — MCP tools are presented to the brain through the same declaration source.
- **$0 check:** $0. Open spec + open SDKs. VERIFY the current spec revision and SDK versions at build time (spec rev. 2026-07-28 cited in Oct 2026 sources).
- **Evidence gate:** Playwright MCP end-to-end on a known site via Piplet's approval flow; a malicious/poisoned tool description (test fixture) is blocked or flagged, never auto-trusted; tool-call budgets enforced (a looping tool is cut off).
- **Risks:** Indirect prompt injection via tool results (treat all tool output as untrusted data; never follow instructions embedded in it); tool poisoning via descriptions (allowlist + review); MCP Apps rendering before approval (gate rendering, §1.3).

### #6 — Sandboxed execution for shell/code: secrets outside, egress allowlisted, full-command approval

- **What:** Run agent-invoked shell/code in an isolated boundary instead of directly on the host: start with the cheapest $0 local option that fits the laptop (OS-level isolation / container with read-only mounts, no secrets, no network except an allowlist), with the agent loop and all secrets *outside* the sandbox. Approval/allowlist checks validate the *full* argument vector (Trail of Bits argument-injection lesson, §1.6), not just the command name. Block the cloud metadata endpoint. Log every sandboxed run (§#2). Evaluate E2B self-hosted (Apache-2.0, Firecracker) only if a cloud sandbox is later needed; do **not** build on the Daytona self-hosted snapshot without verifying its licence/maintenance status (§1.6).
- **Why:** The current host-shell tool is fine for personal use by the owner and unsafe for untrusted repos/content or any B2B use. The lethal-trifecta / Rule-of-Two analysis (§1.6) says the boundary must be structural, not prompt-based.
- **What it replaces:** Direct host execution for agent-invoked commands. Owner-invoked setup/doctor commands stay on the host.
- **$0 check:** $0 local (container/OS isolation on the laptop). Cloud sandbox (E2B hosted) is $0* only inside a verified free tier — do not assume it; VERIFY pricing/concurrency at build time.
- **Evidence gate:** Escape test fixtures (read a secret file, reach the metadata endpoint, exfiltrate over network) all fail inside the sandbox; a legitimate build/test job succeeds inside it; approval covers flags (test `git show --format` / `go test -exec` style injections).
- **Risks:** Over-isolation breaking legitimate jobs (allowlist mounts + egress per workflow, reviewed); sandbox maintenance burden for a solo founder (keep the boundary simple; prefer one mechanism, well-tested, over three).

### #7 — Plan-and-execute + external-signal-only retry, with budgets

- **What:** Add a plan-first mode alongside the current ReAct loop: for predictable workflows, the planner writes the full plan (tool calls + placeholders) up front, workers execute, a solver combines results, and failure triggers *re-planning* (not blind retry). Add Reflexion-style retry gated *only* on external signals (unit tests, validators, tool errors, state diffs, search results) — a written reflection is stored in episodic memory and added to the next attempt. Hard budgets everywhere: max steps, max retries (e.g. 2 reflections), max tokens/cost per run, max time; stop + report + ask instead of looping. Keep ReAct for exploratory work where each step depends on the last result.
- **Why:** Plan-first is cheaper and more predictable (ReWOO ~5× token efficiency, LLMCompiler up to 3.7× latency / 6.7× cost vs ReAct, per papers in §2.3). Self-correction without external feedback makes things worse (Huang et al.) — the external-signal gate is what makes retry safe. Budgets are what make autonomy affordable at $0.
- **What it replaces:** Single-mode looping for all tasks. It extends the existing capped loop (2 rounds, 5 calls/round) into a two-mode system with explicit budgets.
- **$0 check:** $0. Prompt/harness change only; plan-first *reduces* token spend on routine work.
- **Evidence gate:** Eval harness (§#1) shows lower cost + equal-or-better pass rate on routine tasks in plan-first mode; a failing task stops at budget with a clear report (never loops); a self-correction-without-evidence case is refused (test fixture).
- **Risks:** Planner brittleness on novel tasks (fall back to ReAct when the plan's assumptions break); over-planning overhead on trivial tasks (route trivial tasks to direct execution).

### #8 — OpenTelemetry-shaped tracing + local trace viewer (Langfuse/Phoenix-compatible later)

- **What:** Emit a trace per run (spans for model calls, tool calls, approvals, retries; attributes for model/version, tokens, cost, latency, tool + args hash) in OTel GenAI-semconv shape, stored in SQLite, viewable in a minimal local UI (run → steps → what happened, what it cost, where it failed). Design the schema so a later export to self-hosted Langfuse (MIT) or Phoenix (ELv2) is a config change, not a rewrite. Do not deploy Langfuse/Phoenix yet — the SQLite viewer comes first.
- **Why:** Traces without evals are logs; traces *with* evals (§#1) are debuggability + B2B evidence. OTel portability (§1.8) means this work is never wasted. Cost-per-task visibility is what makes the $0 constraint manageable.
- **What it replaces:** Scattered logs + guessing why a run failed. It complements (does not replace) the audit log (§#2): audit = evidence of *what* happened (tamper-evident); traces = *why/how* it happened (debugging).
- **$0 check:** $0. Local SQLite + existing UI. VERIFY the GenAI semconv attribute names at build time (spec still "Development" status in late 2026 — pin the version used).
- **Evidence gate:** A failed eval run can be diagnosed from its trace alone (which step, which tool, which args, what the model saw); cost per run is visible and matches provider usage within rounding.
- **Risks:** Trace volume (sample/retain policy; cap stored tool outputs); semconv churn (pin + isolate the mapping in one module).

### #9 — Voice loop v2: code-mixed ASR evaluation + reply-mirroring + recovery paths

- **What:** Evaluate $0 Indic ASR paths head-to-head on Piplet's own test audio (Hinglish + Tenglish, accents, noise, 8 kHz): faster-whisper (Whisper large-v3-turbo) vs Project Vaani models (MIT — Hindi/Telugu FastConformer + Vaani-tuned Whisper) vs AI4Bharat IndicConformer (MIT). Keep Kokoro (English) + Piper (Indic — verify the Hindi/Telugu voice first) for TTS. Implement the §4.2 patterns: no forced language choice, per-utterance detection, keep original transcript + normalised copy, spoken-number/entity handling, reply mirroring (language + script + register + kept English nouns), confirmation before acting on numbers/IDs, and a defined recovery/handoff path. Voice notes in Telegram/WhatsApp as input; spoken replies as an option, not the default.
- **Why:** Voice is the natural input for phone-as-remote and for SMB users with limited digital literacy — and code-mixing is where generic voice stacks fail (§4.1). This extends the in-flight multilingual *text* UI into voice without reworking it.
- **What it replaces:** Text-only phone control. It does not replace the text UI — voice is an additional channel with the same tools, approvals, and audit.
- **$0 check:** $0 if local models only (Whisper/Vaani/IndicConformer/Piper/Kokoro). $0* if Groq Whisper is used as fallback (within its free tier — re-check limits). Sarvam APIs are paid — do not make them the default path. VERIFY Vaani/IndicConformer model cards, quality, and compute needs on Hugging Face before building.
- **Evidence gate:** End-to-end task tests (not just transcription accuracy) in Hinglish/Tenglish pass at the same bar as text; a code-mixed test set (§#1) is part of the regression suite; a low-confidence turn triggers confirmation/handoff, never a guessed action.
- **Risks:** TTS quality for Indic languages (verify voices with real listeners before promising); on-device compute on the laptop (measure; fall back to smaller models for short clips); voice cloning — never clone a voice without documented permission, and label synthetic audio.

### #10 — Browser reliability layer: receipts, per-site pass/fail, human confirm for irreversible web actions

- **What:** On top of the existing element-first browser tools: (a) every web job returns a structured receipt — done/failed + evidence (final URL, key DOM/text evidence, screenshot reference) — never a bare "done"; (b) a per-site pass/fail log in SQLite (site, task type, result, failure reason) so Piplet learns which sites are reliable; (c) DOM/snapshot-first actions always, screenshot-clicking only as fallback with the user present; (d) human confirmation before any irreversible web action (purchase, submit, send, delete, account change); (e) Playwright MCP (§#5) as the deterministic path for known sites, browser-use-style open-ended browsing only for research jobs that MCP can't do, with the same receipts.
- **Why:** Vendor browser benchmarks are judge-dependent and don't transfer (§1.5). The only honest browser metric is Piplet's own per-site record. Receipts are what make web automation auditable (§#2) and sellable (§3.1).
- **What it replaces:** "The agent says it did it" with evidence. It extends — does not replace — the existing Playwright tools.
- **$0 check:** $0. Local Playwright/Chromium + SQLite. No cloud browser spend.
- **Evidence gate:** A deliberately failing web task returns `failed` with evidence (never a false "done"); per-site log shows the true pass rate after 20+ jobs; an irreversible action without approval is refused (test fixture). Never bypass bot checks/Turnstile — a blocked site goes to Ankush in his own browser (existing rule, keep it).
- **Risks:** Site changes breaking selectors (per-site log + receipts make breakage visible fast); screenshot token cost (DOM-first keeps it low).

### #11 — ONE vertical B2B pilot pack: narrow workflow + evals + HITL + audit + DPDP-ready paperwork

- **What:** Pick **one** narrow, frequent, financially visible workflow for **one** type of small business (candidates already in Ankush's agency work: review-reply automation, appointment reminders/no-show rescue, FAQ instant replies — pick the one with the clearest success metric and the least regulated data). Ship it as a *pack*: the workflow as Piplet skills + tools, the eval golden set for that workflow (§#1), the approval tiers (§#2), the audit receipts, a one-page AI fact sheet (what the agent does, what it never does, where data goes, how to stop it), and DPDP-ready notice/consent templates (§#12). Price it as a small fixed setup + monthly retainer covering model costs (§3.3) — **not** outcome pricing until evals prove the success rate. Run it for one real client (or one realistic pilot with Ankush as the client) before building a second workflow.
- **Why:** Investors and buyers publicly converge on this shape: narrow vertical wedge, reliable task completion, measurable value, secure handling (§3.2). A second workflow before the first is proven is how solo founders diffuse. The pack *is* the product — the platform underneath is Piplet.
- **What it replaces:** Building more platform features before any workflow is proven. It replaces generic "AI automation" pitching with one checkable offer.
- **$0 check:** $0 to build (Piplet + skills + docs). Client running costs (model/API) must be measured (§#8) and covered by the retainer — never absorbed silently.
- **Evidence gate:** Evals on the client's real task distribution (not demos); 100% human review in weeks 1–2 with failure categorisation (Cleverbridge pattern, §3.1); autonomy widened only when the metrics justify it; client can hit the kill switch and read the receipts.
- **Risks:** Scope creep (one workflow means one workflow); regulated data (health/finance — get legal advice, §3.4); promising outcomes before the numbers exist (don't).

### #12 — DPDP-ready data controls: purpose tags, minimisation, retention/purge, notice/consent

- **What:** (a) Purpose-tag every stored datum and check the tag before the agent acts on it for a different purpose. (b) PII redaction/minimisation before cloud model calls (extend the existing "no private data on Gemini free tier" rule into a general redaction step with a local/Groq routing preference for private turns). (c) Retention + purge policy with user/client controls (view, export, delete) and defined log retention. (d) Privacy notice + consent-flow templates for B2B use, in plain language, in the client's language(s). (e) India-region/local inference preference for regulated workloads; documented transfer/contract review for anything else. (f) Breach-notification runbook (72-hour Board notification per DPDP Rules summaries — VERIFY).
- **Why:** The moment Piplet touches another person's data, DPDP duties attach (§3.4), and most fiduciary obligations apply from May 2027 — programmes started now will be live by then, so building controls in now is cheaper than retrofitting. Buyers ask these questions in procurement (§3.1).
- **What it replaces:** Implicit "it's all in SQLite on my machine" data handling with explicit, checkable controls. Personal use stays simple; B2B use gets the controls.
- **$0 check:** $0 (engineering + templates). Legal advice is *not* $0 — budget for qualified advice before selling to regulated sectors; do not treat this file or any template as legal advice.
- **Evidence gate:** A purpose-mismatch action is refused (test fixture); a delete/export request completes end-to-end; redaction is verified on sample prompts (no Aadhaar/phone/medical strings reach cloud calls in test fixtures).
- **Risks:** Over-engineering for personal use (keep personal mode lightweight; controls activate per-client); template law (templates are a starting point, not compliance).

### #13 — Offline/local resilience: quota-aware routing, budgets, and small-model discipline

- **What:** (a) Per-model/per-day usage tracking in SQLite with warnings at 80% of known free-tier limits and automatic demotion to cheaper/local models (Flash-Lite first, hard models for hard turns only — prior cycle's brain fix, now enforced by counters, not hope). (b) Per-run and per-day token/cost budgets with graceful degradation (shorter plans, fewer retries, local model, queue-for-later) instead of hard failure. (c) Small-model discipline: ≤5 tools for local models, context ≥32k, MoE preference on 16GB RAM (prior cycle §2.4 — re-verify model picks at build time, they rotate fast). (d) Offline queue + replay hardening (already built — add eval coverage for restart survival and dead-letter handling).
- **Why:** Free tiers are per-project, unpublished, and changeable (Gemini limits are not in docs). An agent loop can burn a day's quota in an hour. Resilience is what makes $0 *sustainable*, not just $0 on day one.
- **What it replaces:** Hope-based routing. It extends the existing brain chain + offline queue with counters and budgets.
- **$0 check:** $0. Counters + routing logic only.
- **Evidence gate:** A quota-exhaustion simulation degrades gracefully (no crash, no silent wrong answers, user told what happened); a full day of routine use stays inside free tiers in the eval harness.
- **Risks:** Stale limit numbers (re-check AI Studio / provider docs monthly; treat limits as unguaranteed); local-model quality (keep local as fallback, not primary, for tool-heavy work — BFCL reality, §2.2).

### #14 — Multimodal grounding: screenshot + DOM together, document/image understanding with receipts

- **What:** (a) Ground every screen action in *both* the accessibility/DOM snapshot and the screenshot (element-first, vision as confirmation), with the grounded element + screenshot reference in the receipt (§#10). (b) Document/image understanding (read a screenshot, PDF page, photo of a bill/form) via the vision-capable providers, with extracted fields returned *with* the source region/page cited, and human confirmation before acting on extracted numbers/IDs. (c) File-type allowlist + size caps + sandboxing (§#6) for anything opened from untrusted sources.
- **Why:** Vision-only clicking is expensive and flaky; DOM-only misses visual state. The combination is what production computer-use systems converge on, and receipts are what make extracted data trustworthy. Multimodal evals (GAIA-2, MM-τ-p2) show this is now mainstream capability, not a side quest (§1.7).
- **What it replaces:** Screenshot-only vision (currently mocked-test only) with a grounded, receipted version. It does not replace API/shell/browser tools — vision stays the fallback for apps with no API.
- **$0 check:** $0* — vision calls cost image tokens; keep them inside free tiers with budgets (§#13) and prefer DOM/snapshot paths that need no vision call. VERIFY per-provider image pricing/limits at build time.
- **Evidence gate:** A grounding test set (click the right element on known screens) passes at a measured rate, with failures logged per app; an extracted-amount error is caught by the confirmation step (test fixture with a doctored document).
- **Risks:** Prompt injection from screen/document content (treat all on-screen/on-page text as untrusted data — never follow instructions found in it); screenshot token burn (budgets + DOM-first).

## 6. What could NOT be verified in this sweep

Be honest about these before acting on any of them:

1. **Live GitHub star counts, repo statuses, and licence files.** All star counts and licences are as reported by cited secondary sources on their dates. MemPalace's claims (§1.4) rest on a single promotional-seeming source — unverified. Daytona's licence/maintenance status (§1.6) rests on one analysis — verify directly. Re-check every repo's own `LICENSE` file and recent commits before adopting.
2. **Live pricing and free-tier limits.** All prices/limits (Intercom/Zendesk/Agentforce, E2B, Sarvam, Gemini/Groq tiers, Langfuse/LangSmith/Phoenix) are as reported in Oct–Nov 2026 comparison sources. Pricing pages change without notice. Re-check the vendor's own page at build/quote time.
3. **Benchmark scores.** Almost all benchmark numbers are vendor- or paper-reported, often with different harnesses, judges, and model versions. The browser-use/WebVoyager judge-variance finding (§1.5) and the Mem0 methodology disputes (§1.4) show how far a headline number can move. No benchmark was re-run in this sweep. The MIT "95% of pilots" statistic (§3.2) is widely cited and widely debated — verify the underlying report before quoting.
4. **Paper details.** Several papers (§2) were summarised from abstracts and secondary explainers, not full reads. ArXiv IDs marked "commonly cited" were not all re-verified against arXiv in this sweep. Verify any paper claim before citing it in a deck, application, or publication.
5. **Model cards and quality for Indic speech models.** Project Vaani and AI4Bharat IndicConformer look like the best $0 Indic ASR paths, but this sweep read project/round-up pages, not the Hugging Face model cards, eval results, or compute requirements. Sarvam's per-artefact licences are genuinely confusing (permissive vs GPL-3.0 vs commercial API) — read each artefact's own terms.
6. **DPDP Rules details.** The DPDP timeline, retention, and penalty summaries (§3.4) come from compliance guides, not from a direct read of the Gazette text, and this file is not legal advice. Verify against G.S.R. 846(E) and a qualified lawyer.
7. **Anthropic's Oct 2026 subagent guidance and SkillsBench numbers.** Summarised from secondary coverage of Anthropic's post and the benchmark; the primary post/benchmark were not read in full. Verify before citing the 16.2pp figure publicly.
8. **Piplet's live paths.** Nothing in this sweep changes the honest status in `STATUS.md`: desktop/phone/Telegram/WhatsApp/vision live paths remain unproven until they run on Ankush's laptop/phone with his keys. No finding here should be read as "proven on Piplet."
9. **No live browser, no sign-ins, no repo reads.** This sweep used search + fetched page text only. Any claim that requires reading a repo, running code, or checking a live dashboard remains unverified.
